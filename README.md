# 🛡️ Sensor Predictor — сервис предиктивной аналитики инцидентов на коллекторной сети

**Модуль интеллектуального прогнозирования инцидентов для АО «Москоллектор».** Сервис в реальном времени анализирует поток телеметрии с датчиков объектов коллекторной сети и прогнозирует четыре класса инцидентов: **пожар, несанкционированное проникновение (НСД), риск НСД на ближайшие сутки и поломку оборудования**.

> Проект реализован в рамках хакатона по предиктивной аналитике телеметрии инженерных систем.

## 🎯 О проекте

Объекты коллекторной сети АО «Москоллектор» оборудованы десятками датчиков: дым, движение, температура, открытие дверей/люков, насосы, вентиляторы, ИБП, газовые анализаторы. Диспетчеры получают **тысячи тревог в сутки**, значительная часть которых — ложные срабатывания или технические сбои.

**Сервис решает четыре задачи предиктивной аналитики:**

| Задача | Уровень | Горизонт | Бизнес-ценность |
|---|---|---|---|
| 🔥 **Пожарный риск** | объект | 24 часа | Превентивное оповещение до возгорания |
| 🚪 **НСД-классификатор** | событие | мгновенно | Фильтрация ложных тревог проникновения |
| 📅 **НСД-риск** | объект | 24 часа | Планирование патрулирования и охраны |
| 🔧 **Поломка оборудования** | объект | 24 часа | Превентивное обслуживание насосов/ИБП/вентиляторов |

**Ключевая ценность для диспетчера:** вместо потока сырых тревог — **ранжированный список объектов с вероятностью инцидента и уровнем срочности**, плюс автоматическое отсеивание ложных срабатываний.

## 🚀 Запуск проекта целиком

Единый файл запуска — [`backend/docker-compose.yml`](backend/docker-compose.yml). Он объединяет React-интерфейс, Go API и worker, Python ML-сервис, PostgreSQL, Kafka, миграции, импорт справочников и Swagger UI.

### 1. Подготовка

Нужны Docker Engine / Docker Desktop с запущенным Docker daemon и Docker Compose v2 или новее (`docker compose version`). Go, Node.js и Python на хосте не требуются: приложения собираются в контейнерах. При первой сборке нужен доступ к реестрам образов и пакетов.

Освободите порты `3000`, `8083`, `8081`, `8000`, `5433` и `29092`. Отдельный `model/service/docker-compose.yaml` для общего запуска не используется: он поднимает другую инфраструктуру с пересекающимися портами.

Из корня репозитория перейдите в каталог backend. **Все дальнейшие команды Docker Compose в этом разделе выполняются из `backend/`.**

```bash
cd backend
cp -n .env.example .env
```

В `backend/.env` замените `JWT_SECRET` случайной строкой длиной не менее 32 символов и задайте пароли `BOOTSTRAP_ADMIN_PASSWORD`, `BOOTSTRAP_DISPATCHER_PASSWORD`, `BOOTSTRAP_ANALYST_PASSWORD` (не менее 12 символов). Для связи контейнеров обязательно измените адрес из примера:

```dotenv
MODEL_SERVICE_URL=http://model-service:8000
PREDICTION_INTERVAL=60
```

`localhost:8000` из `.env.example` подходит для запуска API на хосте, но внутри контейнера API нужен адрес `model-service:8000`. Адреса PostgreSQL и Kafka для контейнеров уже заданы в Compose. Отдельные `.env` для frontend и модели для этого сценария не нужны; интерфейс по умолчанию работает с реальным API через Nginx.

### 2. Артефакты обученных моделей

Для полного запуска нужны 12 файлов `.joblib`. Они не входят в Git: получите готовые артефакты или обучите модели общим скриптом [`scripts/train_models.py`](scripts/train_models.py). Подготовка окружения, пути датасетов и параметры запуска описаны в [`scripts/README.md`](scripts/README.md). Из корня репозитория, после установки зависимостей и подготовки датасетов:

```bash
python scripts/train_models.py --check-only
python scripts/train_models.py
python scripts/check_models.py
```

Скрипт сохранит артефакты по путям ниже. Если используете готовые файлы, разместите их относительно корня репозитория строго по этим путям (имена сверены с `model/service/app/config.py`):

```text
model/models/
├── fire_risk/saved/
│   ├── fire_risk_model.joblib
│   ├── fire_risk_threshold.joblib
│   └── fire_risk_features.joblib
├── unac/saved/
│   ├── nsd_model_clean.joblib
│   ├── nsd_threshold_clean.joblib
│   ├── nsd_features_clean.joblib
│   ├── nsd_risk_model.joblib
│   ├── nsd_risk_threshold.joblib
│   └── nsd_risk_features.joblib
└── fault_risk/saved/
    ├── fault_model.joblib
    ├── fault_threshold.joblib
    └── fault_features.joblib
```

Compose монтирует эту директорию в ML-контейнер только для чтения. Без артефактов `model-service` не запустится; для проверки приложения без них используйте деморежим ниже.

### 3. Запуск всех компонентов

```bash
docker compose --profile model --profile demo up -d --build
docker compose --profile model --profile demo ps -a
```

Профиль `model` включает настоящие Python-модели, а `demo` — симулятор, отправляющий синтетические события по зарегистрированным объектам каждые 5 секунд. Если события поступают из внешнего источника, запускайте только с `--profile model`, без `--profile demo`.

Compose дождётся PostgreSQL и Kafka, создаст топики и применит миграции. Одноразовый `bootstrap-importer` загрузит справочники из `backend/testdata/objects.csv` и `channels.csv`; исторические события текущая конфигурация автоматически не импортирует. Затем запустятся API, интерфейс и модель. Периодические прогнозы для объектов с поступившими событиями рассчитываются с интервалом `PREDICTION_INTERVAL` (в Compose по умолчанию 60 секунд).

### 4. Проверка и вход

```bash
curl -fsS http://localhost:8083/health/live
curl -fsS http://localhost:8000/health/ready
docker compose logs --tail=100 api worker model-service simulator
```

У работающих API и ML-сервиса проверки должны возвращать HTTP 200. Состояние `Exited (0)` у `migrate`, `kafka-init` и `bootstrap-importer` нормально: это одноразовые задачи. Если запуск остановился, проверьте их вывод через `docker compose logs migrate kafka-init bootstrap-importer`.

| Компонент | Адрес с хоста |
|---|---|
| Веб-интерфейс | http://localhost:3000 |
| Go API | http://localhost:8083 |
| Swagger UI | http://localhost:8081 |
| OpenAPI | http://localhost:8083/api/openapi.yaml |
| Готовность ML-сервиса | http://localhost:8000/health/ready |
| PostgreSQL | `localhost:5433`, база `sensor_predictive`, пользователь/пароль `app` / `app` |
| Kafka | `localhost:29092` |

Откройте веб-интерфейс и войдите под `admin`, `dispatcher` или `analyst` с паролем, заданным в `backend/.env`. Если пароли не меняли, значения для локального демо: `AdminPredict2026!`, `DispatchPredict2026!`, `AnalystPredict2026!` соответственно. Учётные записи создаются при первом запуске API; изменение `BOOTSTRAP_*` не заменяет пароль уже существующего пользователя.

При включённом симуляторе дождитесь поступления телеметрии и ближайшего цикла расчёта, затем проверьте объекты и прогнозы в интерфейсе. Новый запуск без истории позволяет проверить обмен данными, но качество прогнозов требует накопленной телеметрии. Инструкции по импорту собственных CSV есть в [`backend/README.md`](backend/README.md#import-historical-data). Рабочие Kafka-топики общего запуска — `sensor.events.v1` и `predictions.v1`.

### Демо без файлов моделей

После настройки `backend/.env` можно запустить интерфейс и backend с генератором событий и тестовой моделью:

```bash
docker compose --profile mock --profile demo up -d --build
```

Адрес интерфейса и учётные записи те же. `mock-model` публикует тестовые прогнозы в Kafka, но не предоставляет HTTP-сервис `/predict`: ручной запрос нового прогноза из интерфейса требует настоящего `model-service`. Проверка `localhost:8000` в этом режиме недоступна.

Не запускайте `mock` и `model` одновременно, чтобы не получать два независимых набора прогнозов. Перед переключением режима остановите текущий стек:

```bash
docker compose --profile model --profile mock --profile demo down
```

### Остановка и повторный запуск

```bash
docker compose --profile model --profile mock --profile demo down
# Повторный запуск полного стека с синтетической телеметрией:
docker compose --profile model --profile demo up -d --build
```

Обычный `down` сохраняет данные PostgreSQL в Docker volume. Команда `down -v` удаляет этот volume вместе с пользователями, телеметрией и прогнозами; используйте её только для намеренного сброса. У Kafka в текущем Compose отдельный постоянный volume не настроен, поэтому после пересоздания контейнера не рассчитывайте на сохранение сообщений.

### 📂 `service/app/` — основные компоненты

| Модуль | Файл | Назначение |
|---|---|---|
| **Оркестрация** | `main.py` | Главный цикл: консьюмер + два цикла (событийный + периодический) |

| **База данных** | `db.py` | SQLAlchemy-модели `SensorEventDB`, `PredictionLogDB` |
| **Kafka** | `kafka_io.py` | Consumer (`sensor_events`) и Producer (`predictions`) |

---

### 🔧 `config.py` — конфигурация

Содержит:
- **Пути к артефактам моделей** (модели, пороги, списки фичей)
- **Словари типов датчиков** (для корректной фильтрации событий):
  - `FIRE_DETECTOR_TYPES` — исключаются из тревог пожарной модели
  - `NSD_TRIGGER_TYPES` — триггеры НСД с кодами (`КД Дверь`, `КД Люк`, `Стекло`)
  - `FAILURE_VALUES` — значения поломок (`Неисправен`, `Обесточен`, `Питание от батарей`)
  - `FAULT_TYPE_MAPPING` — типы датчиков для модели поломок (насосы, вентиляторы, ИБП, фазы)
- **Периодичность плановых прогнозов** (`prediction_interval`, по умолчанию 3600 сек)

### 🧮 `feature_engine.py` — расчёт фичей

Класс `FeatureEngine` содержит методы для каждой модели:

| Метод | Модель | Фичей | Описание |
|---|---|---:|---|
| `fire_features(df, ts)` | Пожарный риск | 40 | Окна тревог, движения, температуры за 1/3/6/12/24ч + базлайны + предвестники |
| `nsd_event_features(df, ts, trigger_type)` | НСД-классификатор | 9 | Движение до триггера, каскад открытий после, поломки за 14/30д |
| `nsd_risk_features(df, day)` | НСД-риск | 10 | История чистых НСД за 1/7/30д, поломки, плановые работы |
| `fault_features(df, day)` | Поломка оборудования | 21 | Эпизоды поломок, свежесть, пер-типовые счётчики, хроничность каналов |

**Ключевые определения:**
- **Эпизод поломки** = группа событий с разрывом > 7 дней
- **Чистое НСД** = открытие + движение в 5 мин ПОСЛЕ + НЕ снято с охраны за 60 мин до
- **Каскад открытий** = другие открытия в течение 10 мин ПОСЛЕ триггера

### 🔮 `predictor.py` — инференс

Класс `Predictor` загружает артефакты моделей при старте и предоставляет методы:

| Метод | Модель | Возвращает |
|---|---|---|
| `fire_risk(obj, fdict)` | LightGBM | `Prediction(type="fire_risk", risk_score=...)` |
| `nsd_event(obj, fdict)` | Ансамбль | `Prediction(type="nsd_event", risk_score=...)` |
| `nsd_risk(obj, fdict)` | RandomForest | `Prediction(type="nsd_risk", risk_score=...)` |
| `fault_risk(obj, fdict)` | RandomForest | `Prediction(type="fault_risk", risk_score=...)` |

**Уровни риска:**

| `risk_level` | Диапазон | Действие |
|---|---|---|
| `low` | < 0.3 | Информация для аналитики |
| `medium` | 0.3 – 0.6 | Мониторинг, предупреждение |
| `high` | 0.6 – 0.8 | Внимание диспетчера |
| `critical` | ≥ 0.8 | Немедленное уведомление |

---

### 🔄 `main.py` — оркестрация

Класс `ModelService` реализует два цикла:

**Событийный цикл** (`sweep_triggers`):
1. При поступлении триггера НСД событие откладывается на **10 минут**
2. После истечения окна каскада рассчитываются фичи и предсказание
3. Результат публикуется в `predictions`

**Периодический цикл** (`periodic_predictions`):
1. Каждые `prediction_interval` секунд для всех затронутых объектов
2. Считаются три прогноза: пожарный риск, НСД-риск, поломки
3. Результаты публикуются в `predictions`

### 🔥 Пожарный риск (`fire_risk`)

**Задача:** прогнозирует вероятность пожарного инцидента в ближайшие 24 часа.

**Фичи (40):**
- Окна тревог за 1/3/6/12/24 часа + базлайны за неделю
- Движение за 1/6/24 часа + базлайны
- Температура (средняя, максимальная) за 6/24 часа
- Предвестники: затопление, люки, стекло, двери, насосы, вентиляторы
- Временные признаки: час, день недели, месяц, выходные

**Ключевые метрики:**

| Метрика | Значение | Интерпретация |
|---|---:|---|
| **PR-AUC** | 0.875 | Высокое качество ранжирования |
| **Precision** | 0.700 | 7 из 10 алертов — реальный пожар |
| **Recall** | 0.905 | Ловим 90% пожаров |
| **F1** | 0.790 | Отличный баланс точности и полноты |
| **Порог** | 0.3517 | Оптимизирован по максимуму F1 |

**Домен:** только оснащённые объекты (с датчиками дыма или УИР-Р). На неоснащённых объектах пожар физически не наблюдаем.

**Побочный инсайт:** выявлена **карта слепых зон** — значительная часть объектов не оснащена пожарными датчиками (рекомендация по дооснащению для заказчика).

### 🚪 НСД-классификатор (`nsd_event`)

**Задача:** на каждый триггер (открытие двери/люка/стекла) отвечает — **реальное проникновение или ложная тревога**.

**Фичи (9):**

| Фича | Описание | Важность |
|---|---|---|
| `motion_before_30min` | Движение за 30 мин до открытия | Критичная |
| `cascade_openings_10min` | Каскад открытий в 10 мин после триггера | Критичная |
| `failures_14d` | Поломки за 14 дней | Высокая |
| `failures_30d` | Поломки за 30 дней | Высокая |
| `sensor_type_code` | Тип триггера (дверь/люк/стекло) | Средняя |
| `hour`, `dow`, `month`, `is_off_hours` | Временные признаки | Средняя |

**Ключевые метрики:**

| Метрика | Значение | Интерпретация |
|---|---:|---|
| **PR-AUC** | 0.937 | Отличное качество классификации |
| **Порог** | 0.3053 | Оптимизирован по максимуму F1 |

**Результат:** корректно разделяет реальные НСД (скор ~0.8) и ложные тревоги (скор ~0.05), снимая нагрузку с диспетчеров.

### 📅 НСД-риск (`nsd_risk`)

**Задача:** вероятность НСД на объекте в ближайшие сутки. Базируется на идее **near-repeat** — инциденты приходят волнами.

**Фичи (10):**

| Фича | Описание | Важность |
|---|---|---|
| `nsd_prev_30d` | Чистые НСД за 30 дней | 35% |
| `nsd_prev_7d` | Чистые НСД за 7 дней | 32% |
| `nsd_prev_1d` | Чистые НСД за 1 день | 9% |
| `off_guard_prev_7d/30d` | Плановые работы (снятие с охраны) | 14% |
| `failures_prev_7d/30d` | Поломки за 7/30 дней | 4% |
| `dow`, `month`, `is_weekend` | Временные признаки | 6% |

**Ключевые метрики:**

| Метрика | Значение | Интерпретация |
|---|---:|---|
| **Алгоритм** | RandomForest (balanced) | Устойчив к дисбалансу |
| **PR-AUC** | 0.290 | Lift ~9× над бейзлайном (0.0316) |
| **Precision** | 0.284 | Топ-10% концентрируют значительную долю НСД |
| **Recall** | 0.504 | Ловим половину НСД |
| **Порог** | 0.7814 | Оптимизирован по максимуму F1 |

**Применение:** топ-10% самых рискованных объект-дней концентрируют значительную долю реальных НСД — основа для планирования патрулирования.

### 🔧 Поломка оборудования (`fault_risk`)

**Задача:** прогнозирует новый **эпизод поломки** (переход в «Неисправен»/«Обесточен»/«Питание от батарей») на объекте в ближайшие 24 часа.

**Эпизод** = группа событий поломок с разрывом > 7 дней.

**Фичи (21):**

| Группа | Фичи | Описание |
|---|---|---|
| **История НСД** | `nsd_prev_1d/7d/30d` | Чистые НСД за 1/7/30 дней |
| **Поломки** | `failures_prev_7d/30d` | Поломки за 7/30 дней |
| **Плановые работы** | `off_guard_prev_7d/30d` | Снятие с охраны за 7/30 дней |
| **Эпизоды** | `episodes_prev_7d/30d` | Эпизоды поломок за 7/30 дней |
| **Свежесть** | `days_since_last_episode` | Дней с последнего эпизода (16% важности) |
| **Каналы** | `fault_channels_prev_1d`, `fault_events_prev_1d` | Каналы и события за последний день |
| **Пер-типовые** | `pump/fan/ups/phase_eps_30d` | Эпизоды насосов/вентиляторов/ИБП/фаз за 30 дней |
| **Хроничность** | `max_channel_eps_30d`, `repeat_channels_30d` | Максимум эпизодов на канал, повторяющиеся каналы |
| **Календарь** | `dow`, `month`, `is_weekend` | Временные признаки |

**Ключевые метрики:**

| Метрика | Значение | Интерпретация |
|---|---:|---|
| **Алгоритм** | RandomForest (balanced) | Устойчив к дисбалансу |
| **PR-AUC** | 0.2167 | Lift ~3.55× над бейзлайном (0.0611) |
| **Precision** | 0.217 | 1 из 5 алертов — реальная поломка |
| **Recall** | 0.394 | Ловим 40% поломок |
| **Порог** | 0.6615 | Оптимизирован по максимуму F1 |

**Инсайт:** оборудование с движущимися частями (насосы, вентиляторы) и системы питания (ИБП, фазы) ломаются в 10–15× чаще статических датчиков.

## 📈 Методология и инсайты

### Честная оценка

- Все модели оценены на **временном сплите** (тест строго после обучения) — без случайного перемешивания, которое завысило бы метрики за счёт утечки будущего.
- Пожарная модель обучена и оценена **только на оснащённом парке** — чтобы метрики отражали реальное умение, а не знание «где нет датчиков».
- Для поломок и НСД-риска использован **RF с `class_weight='balanced'`** — стратегии SMOTE не дали прироста.

### Методологические находки проекта

1. **Ограничение домена** сильнее добавления фичей (пожар: recall 0.64 → 0.905).
2. **Газовые датчики** — индикатор качества обслуживания, а не предвестник пожара.
3. **Родительский (иерархический) prior нестационарен** — риск объектов волнообразный, не свойство группы.
4. **Статистики формы** (пик/дисперсия/тренд) работают как прокси оснащённости, а не физический сигнал.
5. **SMOTE не помогает** при сложной границе классов — классический `class_weight='balanced'` оптимален.

## ⚠️ Ограничения

### Известные ограничения

- **Таргет «пожар»** = срабатывание дыма/УИР-Р, а не подтверждённый огонь. Модель предсказывает то, на что реагирует диспетчер.
- **Отсутствие сообщений ≠ исправность.** Для неоснащённых объектов прогнозы не строятся.
- **Поломки с дисбалансом ~1:15** — модель полезна как инструмент ранжирования, а не точный детектор.
- **Метрики риск-моделей (НСД/поломки)** скромные по абсолютному значению из-за сильной разреженности целевых событий; их ценность — в **лифте над бейзлайном** (приоритизация).

### Методологические ограничения

- **Фичи должны совпадать 1-в-1** с тренировочными SQL. Любое расхождение = признак дрейфа фичей или утечки данных.
- **Тестовые метрики** получены на исторических данных (2024–2026) и подлежат валидации на новых временных периодах перед промышленной эксплуатацией.
